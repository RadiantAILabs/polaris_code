# Django issue-fixing instructions

**Start with a failing behavior, not a guessed edit.** From the statement, write the public operation, actual result, expected result, and every named variant or boundary: single/bulk, filter/annotation, empty/nonempty, base/subclass, sync/async, old/new format, default/custom manager, or backend. Reproduce on the checked-out version with the smallest possible case. Prefer a new regression method in an existing tests/<component>/ module that fails before the code change; this patch interface can edit existing files but cannot create a new file (Django contributor guidance: docs/internals/contributing/new-contributors.txt:26-29 and writing-code/submitting-patches.txt:271-273). Statements usually name at least two paths, modes, or boundary inputs, so check the whole list before submitting.

Use only the supplied checkout at `/testbed` for Django source and behavior. Do not download or install another Django release, clone or fetch Django's upstream repository, or fetch PR diffs or PyPI files for comparison. If a version comparison cannot be established from local files, report the uncertainty. Installing a missing non-Django dependency is fine.

**Find the owning layer by following the value.** Search the public method or test first, then the dispatch hook, and finally the producer and consumer of the wrong result. In ORM code, a Manager may change the starting QuerySet; QuerySet methods build a Query; double-underscore names resolve through registered Transform/Lookup classes; SQLCompiler and backend operations generate SQL and convert returned values. Search the terminal lookup name, get_lookup/get_transform, resolve_expression, compiler.compile/as_sql, connection.features, and as_postgresql/as_mysql/as_sqlite/as_oracle as relevant. Do not stop at a plausible QuerySet method if the observed difference occurs in SQL or after fetching a row (django/db/models/query_utils.py:212-250; django/db/models/sql/query.py:1246-1277; django/db/models/sql/compiler.py:1481-1515,1810-1850; docs/ref/models/lookups.txt:15-29,97-121). For deletion, start at Collector.can_fast_delete/collect/delete and inspect signals, cascades, and related fields (django/db/models/deletion.py:96-115,187-225,305-371). For migrations, separate Autodetector state comparison, Operation.reduce/Optimizer, and Writer/deconstruct/import paths (django/db/migrations/autodetector.py:21-58; optimizer.py:1-65; docs/topics/migrations.txt:420-440,641-657).

For forms, follow Field.clean → to_python/validate/run_validators, then MultiValueField subfields/compress or ModelForm Meta/metaclass/factory, as appropriate (django/forms/fields.py:170-200,1048-1148; django/forms/models.py:245-313,557-635). For middleware, trace BaseHandler.load_middleware and adapt_method_mode through both sync and async chains (django/core/handlers/base.py:26-104). For sessions, pair encode and decode with the actual engine and settings (django/contrib/sessions/backends/base.py:92-115). For CLI or serialization, follow parser/subparser or serializer/related-manager/QuerySet rather than the surface call (django/core/management/base.py:47-83; django/core/serializers/python.py:64-90). These are starting maps; confirm names in the current checkout.

**Use run_python to get evidence.** For pure forms, validators, expressions, or parser logic, execute a short direct Python assertion. For basic ORM behavior, configure a fresh SQLite database and SECRET_KEY with settings.configure(), call django.setup(), define models with a temporary app_label, and create tables with connection.schema_editor(); for relation discovery or transactions, extend the nearest existing Django test instead (docs/topics/settings.txt:191-209,275-292; docs/ref/schema-editor.txt:19-24; docs/topics/testing/tools.txt:876-939,1523-1552). A quick single-method suite run can be launched from a run_python script using Python to invoke tests/runtests.py with a dotted method label, --parallel=1, and --noinput. The tool itself has a 30-second timeout; keep pre-patch checks small. Django's runner, not a project manage.py, owns core tests (docs/internals/contributing/writing-code/unit-tests.txt:199-230).

**Patch the layer that owns the invariant and audit peers.** Search for sibling implementations of the changed hook and the paired operation named in the statement. Check read/write converters, create/bulk_create, filter/annotation, encode/decode, sync/async, default/custom manager, base/subclass, and backend overrides when applicable. An empty bounded search may be truncated; narrow its path before inferring absence. A sampled review rejected broad base-class refactoring without tests for it and raised third-party subclass effects ([PR review](https://github.com/django/django/pull/18070#discussion_r1581874112), [follow-up](https://github.com/django/django/pull/18070#discussion_r1604045639)). Preserve old public calls, import paths used in migrations, stored formats, and subclass hooks unless the requested behavior deliberately changes them. For an intentional incompatible API change, use Django's deprecation warning, test, documentation, and timeline process (docs/internals/release-process.txt:81-119; docs/internals/contributing/writing-code/submitting-patches.txt:170-225).

**Verify the named behavior, then adjacent regressions.** Run the new method and its module through python tests/runtests.py; use --parallel=1 for full tracebacks, --debug-sql for SQL diagnosis, and assertNumQueries when the claim is query count (docs/internals/contributing/writing-code/unit-tests.txt:447-515; docs/topics/testing/tools.txt:1922-1939). SQLite is the bundled default; a SQLite pass is not evidence for PostgreSQL/MySQL/Oracle behavior or an optional-dependency skip. Use connection.features and backend-specific tests where the behavior depends on them (docs/internals/contributing/writing-code/unit-tests.txt:156-161; docs/topics/testing/tools.txt:2206-2218). Add a boundary or error-path test when it distinguishes the fix: unrelated closed Django reviews asked for exactly that ([PR review](https://github.com/django/django/pull/18001#discussion_r1534537425), [PR review](https://github.com/django/django/pull/18007#discussion_r1581903296)). Update docs for new or changed public behavior. A stable backport may need a patch-release note; a main-branch-only bug fix does not automatically need one (docs/internals/contributing/writing-code/submitting-patches.txt:271-302). Report tests actually run and any backend, dependency, or timeout limit.
