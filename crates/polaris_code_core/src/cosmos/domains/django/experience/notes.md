When fixing a Django issue, turn the report into a short behavior list before editing. Include every named mode and operation: creation versus bulk creation, synchronous versus asynchronous handling, positive versus negated query, empty versus populated input, and any other variants the report actually names. Mark which cases your check covers.

Locate the path that produces the value, the path that consumes it, and the nearest existing tests. Use a scoped search for sibling variants such as subclasses, alternate serializers, field types, lookup operators, backends, and factory wrappers. Read the relevant source range after a truncated search. A search with a limit does not establish absence. Make the smallest change that preserves behavior outside the reported case, and confirm the replacement text is unique in the inspected file.

Build a minimal executable regression check. Make its assertion fail on the original code for the reported behavior, then pass with the proposed change. Check an actual downstream result when possible: returned Python value, decoded data, queryset rows, rendered form errors, command exit and stderr, or serialization round trip. SQL text and mocked method calls can help locate a fault, but also exercise the behavior they stand in for. For a query involving dates or emptiness, include boundary values and both matching and nonmatching rows. For a lifecycle or race report, exercise the real lifecycle if the environment permits; a direct method call alone leaves that behavior unproved.

Run the nearest focused Django test module after the change when it can run within the available tools and time. Keep the issue-specific check as well. If a test cannot import Django or a dependency, first identify the checkout and interpreter actually in use; treat an import or setup error as infrastructure, not as evidence that the patch fixes the bug. Avoid repeating package installation and broad exploratory commands once the relevant environment is known.

Review the final diff before submitting. Remove temporary check scripts, test apps, downloaded files, and unrelated edits. Keep the regression script in the offered check field or the tool's scratch area, not in the project patch. If you could only verify a proxy for the reported behavior, say exactly which behavior remains untested. A passing self-authored check is evidence for its assertions, not proof of complete resolution.
