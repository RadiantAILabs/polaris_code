# Integration Guide

This guide goes from a goal to the `polaris_code` plugins and seams that satisfy
it. It is the reverse index of the [plugin catalog](../../crates/polaris_code/src/docs/plugins.md):
the catalog answers "what does this plugin do?", this guide answers "I want to
do X — what do I register or extend?".

`polaris_code` is a coding agent first, so most of this guide is aimed at
contributors extending the agent. The exception is the last four rows: a program
that only wants to *drive* a turn — an eval runner, a test harness, a second
front end — starts at the [embedding
guide](../../crates/polaris_code/src/docs/embedding.md) instead, and needs
none of the rest.

## Common Integration Patterns

| Goal | Register / extend | Notes |
|------|-------------------|-------|
| **Let the agent read/edit/create files** | `CodeToolsPlugin` (needs `ToolsPlugin`) | Sandboxed to `working_dir`; `edit_file` and `create_file` are gated `ToolPermission::Confirm` as one, and `create_file` refuses a path that already exists. |
| **Query the codebase as a graph** | `CodeGraphPlugin` (needs `ToolsPlugin` + ontrace's `OxigraphPlugin`) | Deterministic Rust→triples indexer + SPARQL-backed symbol/def/ref queries over the Code `ABox`. |
| **Start without indexing the working directory** | `CodeGraphPlugin::with_boot_index(false)` | `ready` skips the boot index pass. The graph tools still register and answer that the index was not built, and edits still refresh the files they touch. `polaris` passes `false` for an interactive run whose directory is not a project (the home directory, the filesystem root, or no project marker in it or an ancestor below home) and says so in a startup note; a headless run always indexes. A host that makes the same choice calls `tools::boot_index_wanted(headless, dir)` and passes the result to `with_boot_index`. |
| **Give the agent recall/memoization** | `MemoryToolsPlugin` | Reflective memory: memoize/recall conclusions, content-hash invalidated. |
| **Show graph progress in the TUI** | `ProgressMiddlewarePlugin` | Bridges graph instrumentation events to the conversation panel, and to the Graph tab's `GraphFeed` when the shell has one; without the feed it only feeds the conversation. |
| **List the tabs the interactive shell shows** | `tabs::add_shell_tabs(&mut server, log_buffer, &agent)` (needs `polaris_tui::TuiPlugin`) | Adds Graph and Help, plus the log capture the conversation panel's `Ctrl-O` node timeline reads, which has no tab of its own. Add the conversation plugin *after* this call and it is the first tab; tabs appear in the reverse of the order their plugins are added. Without `TuiPlugin`, `Server::finish` returns an error naming the missing `TuiRegistry`. |
| **Show the graph of the coding agent with plugin steps** | `tabs::add_code_agent_shell_tabs(&mut server, log_buffer)`, or `graph_view::GraphViewPlugin::for_code_agent_steps()` with `GraphPanelPlugin` | Like `add_shell_tabs`, but the Graph tab draws `CodeAgent::with_steps` built from the step registry after every plugin has built, so added steps appear by name. Needs `CodeAgentPlugin`. `polaris` starts this way. |
| **Show your agent's graph in a tab** | `graph_view::GraphViewPlugin::for_agent(&agent)` (needs `polaris-tui`'s `GraphPanelPlugin`) | Publishes the agent's graph to the Graph tab's `GraphFeed` as the default. The tab matches nodes by name, because a session builds its own copy of the graph. `add_shell_tabs` already adds both plugins. |
| **Make the Graph tab draw the graph a host actually runs** | `graph_view::announce(ctx, name, &graph)` | A host that builds its own executor, as `cosmos::host` does for a selected topology, calls it just before executing and keeps the returned guard until the run returns; the tab then draws that graph with node ids that match the run. Returns `None` and does nothing when the context has no `GraphFeed`. |
| **Run `/commands` and complete `@` files in the TUI** | `terminal::attach(ConversationPanelPlugin, Arc<CommandRegistry>, working_dir)` | Wraps the panel's `UserIO` in `CommandDispatch` (commands answered locally, never sent to the model; `@` mentions outside `working_dir` refused) and supplies `WorkspaceFiles` for `@` completion. |
| **Add a terminal command** | `CommandRegistry::register_sync` / `register` | Appears in the `/` popup and `/help`; the handler runs in-process and replies in the transcript. |
| **Browse or switch coding sessions** | `/sessions`, `/new [id]`, `/resume [number\|id]` | Uses the repository's `.polaris/sessions` `FileStore`; saves before switching and replays canonical messages without executing them. `/sessions` (and a bare `/resume`) is the picker: it numbers the saved sessions newest first and `/resume <number>` chooses a row, so resuming needs recognition rather than an identifier. Give `SessionNavigation::with_store` the same store the `SessionsPlugin` was built with and each row also carries turn count, start time and opening prompt; without it the rows are identifiers only. At most 20 rows are numbered; the rest are counted and reachable by `/resume <id>`. An empty repository points at `/new`. |
| **Run the reflective coding loop** | `CodeAgentPlugin` (needs `SessionsPlugin`) | ReAct loop; each decision reads `PolicySnapshot` and writes a reified `Decision`/`ToolCall` into the Session `ABox`. |
| **Ask a person to approve tool calls** | `InteractiveApprovalPlugin`; to use your own input transport, insert `HumanApproval::new` with your `HumanApprover` instead | The default asks over each session's existing `UserIO`. A replacement `HumanApprover` must be `Send + Sync`, and the scope it returns is checked against the choices offered. With no approver installed, calls that still need a person are denied; calls that policy allows outright run as before. |
| **Run one coding task non-interactively (CI, eval, scripting)** | `polaris -p "<prompt>"` (`exec::ExecIOPlugin` instead of the TUI panels) | Runs one turn via `run::drive_turn` and exits; `--output-format text\|json\|stream-json`; `--session <id>` resumes. Exit codes: `0` completed, `1` failed, `2` usage/config error, `130` interrupted. |
| **Let a long command keep running without holding the turn** | `Ctrl-T` in the conversation panel, with `ConversationPanelPlugin::with_background_handle` wired to `BackgroundCommands::request_background` | Offered only for `run_command`, only after the permission gate resolved, and refused in words otherwise. Backgrounding **hands the wait to the host and nothing else**: no `start`, no `execute`, no second spawn. The tool runs as a `ToolRun` — a task of its own — because `run_command`'s run is *reserved* for its `execute` caller (`ShellExecutor::wait_for` refuses it) and that caller's handle stops the child when dropped; the turn stops waiting on the task and `BackgroundReporter` waits on it instead, receiving the same `executed` response the model would have. The invocation closes once, with a normal `tool_result` naming the task. It does **not** buy the command more time: the deadline is fixed at start, so every surface that names a task names what is left of it. |
| **Let the model start a long command itself** | `TaskToolsPlugin` (needs `ToolsPlugin` + `ShellPlugin`) → `run_in_background`, `task_output`, `stop_task` | The model's own way in, over the same `ShellExecutor` and the same `BackgroundTasks` table the chord writes, so a model-started task is in `/tasks` too. `run_in_background` starts the command, detaches it and returns a task number in the same turn; the deadline defaults to `BACKGROUND_DEFAULT_TIMEOUT_SECS` (one hour) rather than the foreground 120s. `task_output` reads a bounded tail while the task runs and its full capture plus exit status once it ends, including a task that ended while no turn was active — the host keeps the last `FINISHED_RETAINED` results. Every read says what it truncated or dropped. Gated identically to `run_command` via `SHELL_EXECUTION_TOOLS`; the request carries no `ShellCancel`, so Ctrl-C ends the turn, not the task. |
| **Let the model read a web page** | `WebToolsPlugin` (needs `ToolsPlugin`) → `web_fetch` | Fetches an `http(s)` URL from a public host and returns HTML as markdown or text as it is, with the final URL and content type; a long page comes back in pieces and the last line names the `offset` for the next. Loopback, private-network and link-local addresses are refused on every redirect hop. Registered `Confirm`, so attended modes ask and an unattended run needs the tool granted by name. Pass `WebToolsConfig` to change the time, redirect and size limits. See [web access](../web-access.md). |
| **List, inspect, follow or stop those tasks** | `BackgroundCommands::register(&CommandRegistry)` → `/tasks [--all]`, `/task <id>`, `/fg <id>`, `/stop <id>` | `/tasks` lists the **current session** by default and says when it is hiding tasks from others. `/stop` is `ShellExecutor::stop(id)` — stopping a *process*, not interrupting a *turn*; the two are never routed through each other, so Ctrl-C on a turn leaves a backgrounded task running. `/fg` re-attaches your attention only: the tool call closed when the task was backgrounded and does not reopen. Wire `BackgroundReporter` to close each task's block when it ends. |
| **Interrupt a running turn** | Ctrl-C in the conversation panel, or SIGINT/SIGTERM with `--print` | Raises the upstream per-turn token. The real agent races parked input, model streaming, and each tool await; interrupted tools receive a paired error result. The TUI continues to the next prompt. Headless takes the same cooperative route for either signal — cancel, save, report — and exits `130` for both, because a cancelled turn's exit code is `RunReport`'s, not the signal's; a *second* signal exits immediately without saving, `130` for SIGINT and `143` for SIGTERM. Status messages use `io_type = "interrupting"` then `"cancelled"`. |
| **Keep an interactive session's work** | `run::persist_turn` after every turn, `run::shutdown_driver` at exit | A checkpoint capture is in-memory; nothing is on disk until a save. `persist_turn` runs between turns, where the context lock is free, and names the session the turn was driven in — after a `/new` or `/resume` that is not the launch identity. |
| **Exit an interactive session on a signal** | `run::stop_signal` (SIGINT *and* SIGTERM) selected against the TUI waiter, then `run::shutdown_driver` | `shutdown_driver` is the one safe order: quiesce the in-flight turn, abort the driver so it releases the context lock it holds while parked on input, then save. Exit codes `0` clean quit, `130` SIGINT, `143` SIGTERM. |
| **Decide whether a failed turn ends the session** | `run::drive_turn_step` → `run::DriverStep`, bounded by `run::FailureBudget` | `Recover` for `Execution`/`Persistence`/`Store` — the turn ran and something inside it broke, so say so in the transcript and go back to the prompt. `Stop` for everything else, which is a property of the session and fails identically next time, before the graph ever parks on input. Three consecutive recoverable failures stop anyway: a driver that never exits is a worse bug. |
| **Add a new run-surface front end** | extend `src/run.rs` (`drive_turn`/`drive_until`) | Both existing front ends already share this; a third caller (e.g. an ACP/MCP surface) reuses it rather than looping `process_turn_with` itself. Reuse `persist_turn`/`shutdown_driver` too — they are free functions on purpose, so no front end needs a type that owns the loop, the session identity and the signal handling together. |
| **Preview the content an edit would write** | `tools::edit_match::plan_edit(original, old, new, replace_all)` | The same pure planner the file tool uses, including its final-newline allowance. Returns updated content or a structured refusal; performs no I/O and grants no write permission. |
| **Add a new tool** | a new `#[toolset]` + plugin under `src/tools/` | Self-contained module + plugin; register with `ToolRegistry`. Add it to the plugin catalog. |
| **Add a new agent decision seam** | extend `policy` (read) and `trajectory` (write) under `src/agents/` | Keep the read-policy / write-trajectory discipline; don't hardcode behavior in the loop. |
| **Refuse, ask about or allow a tool call from code** | a plugin that depends on `PermissionRulesPlugin`, calling `PermissionRules::add_code_rule(name, rule)` in its `build` | The rule is a plain function of the tool name, the call's arguments and the workspace root, and returns no opinion or a `RuleDecision` with a reason. It is weighed with the permission-file rules: deny wins over ask, which wins over allow, and an allow never goes above the mode or the ceiling. Project trust does not apply. A rule that panics refuses the call. For `run_command` and `run_in_background` the rule sees the whole command and then each simple command. Rules are fixed once the server is ready, and `/permissions` lists them by name. See [permission modes](../permission-modes.md#rules-written-in-code). |
| **Bound the complete conversation independently of context projection** | `ContextManager::set_message_limit(N)` in a session setup contribution | Off by default. Counts system, task, each assistant reply, each tool result, and standalone user feedback. An append may reach N; a model call requires fewer than N. Excess appends are rejected, and the next checked boundary ends the turn as a failure with a `Message limit reached/exceeded` explanation and exit 1. Tool effects before result rejection are retained. Projection or compaction never replenishes the count. |
| **Extend session configuration without replacing its resource factory** | `CodeAgentSteps::configure_session(key, callback)` | Runs after stock setup on creation and resume, in ascending key order; errors refuse the session. Use `AgentConfig::prompt_sections` for ordered additions after the role and project grounding. Contributions are frozen with the steps. |
| **Add a step to the coding loop** | a plugin that depends on `CodeAgentPlugin`, calling `CodeAgentSteps::after_tools` or `before_finish` in its `build` | Steps are ordinary graph systems that run after each round of tool calls or on a candidate answer, which they may hold. The agent must be registered with `CodeAgent::with_steps`; `startup::Host` does so. See the [step module](../../crates/polaris_code/src/agents/code_agent/steps.rs). |
| **Validate host inputs before credentials or provider setup** | `startup::Host::configure` | Runs once after parsing and working-directory resolution, before plugins or providers start. Set `LaunchOptions::auto_route = false` to keep ordinary prompts on the conversational path; explicit topology requests still work. A host may also supply `LaunchOptions::model_request_timeout` as a fallback below explicit stock settings. Unused by the stock binary. |
| **Start `polaris` with plugins or settings of your own** | `startup::Host::new().arg(..).plugins(..).run(args)` | The same agent, flags, configuration files, environment variables, providers and front ends as the binary, with the host's plugins added after all of `polaris`'s own and its own command-line settings parsed with the rest. Plugins may depend on any plugin the startup adds, notably `PermissionRulesPlugin` (code rules) and `CodeAgentPlugin` (steps). `run` returns the exit code; the caller exits with it. See the [`startup` module](../../crates/polaris_code/src/startup.rs) for the plugin order, and `tests/host_startup.rs` for a host with a rule and steps run against a scripted model. |
| **Record each collected attempt or the final classified turn** | `AgentConfig::model_observer`, `agents::observation::TurnObserver` | Optional host callbacks. Graph hooks remain the first choice for system/graph events; the attempt observer adds partial billed/cache tokens unavailable after a failed call, and the turn observer sees driver classification and usage before reporting. A turn observer may project final report text without editing canonical history. |
| **Track token usage / cost** | read `TokenMeter` (global) | Consumer-facing; `summary(model_id)` formats the session total + estimated cost. |
| **Read what a headless run spent, from a script** | `--output-format json` and read `usage`, or `stream-json` and read the closing `io_type = "usage"` message | One versioned shape, `polaris-code-run-usage/v1`, built by `TokenMeter::snapshot` and emitted by `exec::usage_message`: four token tiers, estimated USD, model id and price-table identity. The mid-stream `io_type = "tokens"` deltas are a display signal, not the accounting. See [headless usage accounting](../headless-usage-accounting.md). |
| **Drive a turn from your own program (embed the agent)** | compose the plugins yourself, create a session with an `AgentConfig`, call `run::drive_turn` | There is no `Harness` type, no builder and no `init()` — the entry point is the run surface plus the plugins you choose. Read [`src/docs/embedding.md`](../../crates/polaris_code/src/docs/embedding.md) for what you must supply, what the outcome hands back, and what an embedder **cannot** do (notably: `PolicySnapshot::defaults()` is not a safe posture). Runnable: `examples/embed_turn.rs`; proved: `tests/embedding_entry_point.rs`. |
| **Run several isolated agent calls on one server** | one session per call: `AgentConfig::{system_prompt, command_globs, max_output_tokens}` (`with_system_prompt`, `with_command_globs`, `with_max_output_tokens`), a `TokenMeter` of the call's own with `set_task_cost_cap`, and `tools::CallRoot` | Each call gets its own prompt, command list, output limit, spend cap and tool folder. The folder is `AgentConfig::working_dir`, which the agent passes to its tools as a `CallRoot`; the file tools, `run_command` and `run_in_background` follow it. The code-graph, memory and MCP tools stay server-wide. A command list is text matching, not a file or privilege boundary. Read [`src/docs/embedding.md`](../../crates/polaris_code/src/docs/embedding.md#running-several-isolated-calls-on-one-server); proved: `tests/call_isolation.rs`. |
| **Apply one provider policy to every model call** | `ModelsPlugin` + `ModelRunPlugin::new(provider, ModelRunOptions { max_output_tokens, reasoning_effort, .. })` in place of the provider's own plugin | `ModelRunPlugin` wraps the provider once at the `ModelRegistry`, so the main loop, retries, context summaries, reviewers and topologies all get the same output ceiling and pinned effort. A caller may ask for less output, never more. Do not also register the same provider name through its ordinary plugin. Use `with_registry_name` to register under an alias. See [unattended runs](../unattended-runs.md) and [`src/docs/embedding.md`](../../crates/polaris_code/src/docs/embedding.md). |
| **Get a reconstructable ATIF trajectory of a run** | the CLI: `polaris -p "<prompt>" --trajectory-path PATH`; embedded: `RunTrajectory::create` in the host, a clone in `ModelRunOptions::trajectory` and another in `server.insert_global`, `finish(exit_code)` at the end, then `trajectory::rebuild_request(document, step_id)` | The host owns the recorder. Create it before the first model call and before server startup: the model-run plugin records each provider call and the coding context records tool results from the global copy. Call `finish` after tool cleanup and session persistence; it also writes the tool results and messages recorded since the last model call, which a hard kill before then can lose. Read `check`/`finish` for a retained write failure. The file holds task content and full prompts, so treat it as sensitive. `rebuild_request` returns the exact native request of one call from its one-based step id, also after compaction. The format and its limits are in [unattended runs](../unattended-runs.md#trajectory-export); embedding steps are in [`src/docs/embedding.md`](../../crates/polaris_code/src/docs/embedding.md). |

For the full boot wiring, see `crates/polaris_code/src/startup.rs`; `main.rs` only calls it.
